# Day4 订单预警风险管控系统 - 需求分析与详细设计

## 1. 需求分析

### 1.1 核心需求
- **预警次数显示**：支持显示"第N次预警"的预警次数统计
- **权重表管理**：独立的省份、渠道、电话号码维度管理
- **风险管控**：基于多维度权重的智能风险评估和阻断机制
- **阻断管理**：支持渠道阻断、解除阻断、阻断轨迹记录

### 1.2 风险权重计算规则
- **身份证修改**：>3次(+30)，每多一次(+10)
- **手机号修改**：>3次(+30)，每多一次(+10)  
- **注销重注册**：>2次(+30)，每多一次(+10)
- **同手机号注册**：>3次(+10)，每多一次(+10)
- **特殊产品**：每订单(+2)
- **无有效保单**：(+5)
- **连续预警**：>3次阻断
- **订单数量**：>50个/小时阻断
- **连续天数**：5天中有3天预警阻断
- **总权重**：>60分阻断

### 3.2 核心流程设计

#### 3.2.1 预警检测流程
```
订单创建 → 预警检测 → 权重计算 → 阻断判断 → 预警记录 → 通知发送
    │           │         │         │         │         │
    │           ▼         ▼         ▼         ▼         ▼
    │     检查监控范围  计算风险权重  检查阻断条件  保存记录   发送通知
    │           │         │         │         │         │
    └───────────┴─────────┴─────────┴─────────┴─────────┘
```

#### 3.2.2 权重计算流程
```
获取权重记录 → 重置日统计 → 计算各项权重 → 汇总总权重 → 更新记录
     │            │            │            │            │
     ▼            ▼            ▼            ▼            ▼
  查询/创建    检查日期变化   各项规则计算   累加权重值   保存到存储
```

## 4. 设计决策分析

### 4.1 为什么这样设计？

#### 4.1.1 分层架构
- **优势**：职责清晰、易于维护、支持扩展
- **考虑**：避免过度设计，保持简单性

#### 4.1.2 配置化管理
- **优势**：灵活调整、无需重启、支持动态配置
- **考虑**：配置项过多可能增加复杂度

#### 4.1.3 内存存储
- **优势**：性能高、响应快、适合测试
- **考虑**：数据持久化、集群扩展

### 4.2 其他简单方案对比

#### 4.2.1 方案A：数据库直接查询
```
优点：实现简单、数据持久化
缺点：性能差、扩展性差、难以支持高并发
```

#### 4.2.2 方案B：Redis + 数据库混合
```
优点：性能好、数据持久化
缺点：复杂度高、维护成本高
```

#### 4.2.3 当前方案：内存 + 配置化
```
优点：性能最好、实现简单、配置灵活
缺点：数据不持久、重启丢失
```

**选择理由**：当前是学习项目，优先考虑简单性和性能，后续可平滑升级到Redis方案

### 4.3 高并发支持分析

#### 4.3.1 订单生成接口并发分析
```
并发场景：大量订单同时创建
影响分析：
├── 预警检测：同步执行，可能阻塞
├── 权重计算：CPU密集型，可能影响响应
├── 阻断判断：内存查询，影响较小
└── 数据存储：内存操作，影响较小
```

#### 4.3.2 性能优化策略

##### 4.3.2.1 异步处理
```java
// 当前实现：同步处理
public void checkOrderAlert(OrderDTO orderDTO) {
    // 预警检测逻辑
}

// 优化方案：异步处理
@Async
public CompletableFuture<Void> checkOrderAlertAsync(OrderDTO orderDTO) {
    return CompletableFuture.runAsync(() -> {
        checkOrderAlert(orderDTO);
    });
}
```

##### 4.3.2.2 批量处理
```java
// 批量预警检测
public void checkOrderAlertsBatch(List<OrderDTO> orders) {
    // 批量处理逻辑
    orders.parallelStream().forEach(this::checkOrderAlert);
}
```

##### 4.3.2.3 缓存优化
```java
// 权重记录缓存
@Cacheable(value = "weightRecords", key = "#alertKey")
public WeightRecordDTO getWeightRecord(String alertKey) {
    // 查询逻辑
}
```

#### 4.3.3 阻塞影响评估
```
当前阻塞点：
├── 预警检测：中等影响（CPU计算）
├── 权重计算：中等影响（复杂计算）
├── 阻断判断：低影响（内存查询）
└── 数据存储：低影响（内存操作）

优化后预期：
├── 预警检测：低影响（异步处理）
├── 权重计算：低影响（异步+缓存）
├── 阻断判断：无影响（内存查询）
└── 数据存储：无影响（内存操作）
```

## 5. 扩展性设计

### 5.1 水平扩展
- **无状态设计**：服务无状态，支持多实例部署
- **配置中心**：支持配置热更新，无需重启

## 6. 总结

### 6.1 设计优势
- **简单性**：架构清晰，易于理解和维护
- **性能性**：内存操作，响应速度快

- **扩展性**：分层设计，支持功能扩展

### 6.2 适用场景
- **学习项目**：适合学习和理解系统设计

- **异步化**：引入异步处理提升并发性能
